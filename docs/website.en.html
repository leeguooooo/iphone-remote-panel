Two-stage setup; WDA is required

The installer stages the daemon and LaunchAgent. You must then build, sign, install, and relay WDA on the target phone. Timing depends on Xcode, signing, and device state; there is no fixed-minute promise.

# 1) Install the verified Release app; pin its skill and WDA helper to the tag commit $ curl -fsSL https://raw.githubusercontent.com/leeguooooo/iphone-use/main/install.sh | sh # 2) Required: connect, trust, and unlock the iPhone, then complete WDA setup $ ~/.iphone-use/setup-wda.sh doctor $ ~/.iphone-use/setup-wda.sh $ ~/.iphone-use/setup-wda.sh status # The verified agent skill and Claude discovery link are already installed

You need full Xcode, an Apple development team, iPhone Developer Mode, pairing/trust, an unlocked and awake phone, and iproxy. The normal path requires USB and does not auto-switch to Wi-Fi or socat.

The app is checked against the corresponding Release asset SHA-256; helpers and skill use the tag's exact commit. Skill fetch, validation, discovery-link, or installation failure aborts before daemon replacement; a later daemon failure restores the previous skill. Piping into IPHONE_USE_SKIP_SKILL=1 sh is an explicit degraded opt-out, and makes no daemon/skill compatibility claim.

On upgrade, an older plist with no backend key but a valid loopback WDA URL migrates to Direct. Only a legacy install with no WDA configuration stays on Mirror; an explicit backend remains unchanged.

The Direct path

Video, control, and recovery stay attached to one persisted target. If WDA is unavailable, the request fails; the daemon does not silently switch to Mirroring or move the Mac cursor.

VIDEO · 9100

Live WDA MJPEG

The daemon proxies the phone's port 9100 stream at /agent/mjpeg. A broken stream reports failure or a visible degradation; it never switches to legacy WebRTC.

CONTROL · 8100

On-phone input with acknowledgements

Browsers use /control; agents use /agent/input. WDA performs taps, gestures, and Unicode input on the phone. Only a successful HTTP response counts as completion.

LIFECYCLE · UDID

Pinned target, observable recovery

PHONE_REMOTE_UDID is the canonical target; one request cannot temporarily switch phones. Status distinguishes releasing, released, and reconnecting.

CJK input: clean vs mangled

These are component-level records from the same phone. They prove WDA Unicode input works, not that the whole Direct browser path has passed acceptance.

The agent API

Use a see → act → verify loop. Every state-changing POST requires X-Phone-Control: 1 as a CSRF/intent guard in addition to authentication; GET does not. The current MCP server exposes twelve tools for status, screenshots/elements, snapshot-bound and strict-label taps, scroll, text, keys, shortcuts, fail-closed multi-step phone_run_steps, and phone_reconnect, which can only recover the canonical managed Direct target. Its client adds the mutation header automatically. The normal app install supplies the release-matched bridge at ~/Applications/iPhoneUse.app/Contents/MacOS/iphone-use-mcp; users do not have to assemble it from source. The same binary provides flow validate/run for offline validation and one-command replay of reviewed version-1 JSON; --input key=value injects text only for the current run, with no model on the happy path. The browser control bar also provides Flow recording: it keeps only acknowledged actions, prefers semantic labels, discards literal typed values into runtime placeholders, and saves or executes only after review and an explicit safety gate. A later session can open the saved script, restore its reviewed steps after strict validation, fill fresh parameters, and replay it without a model.

# First require the pinned target to be actionable $ curl -H "$AUTH" $HOST/agent/status {"backend":"direct","target_configured":true, "managed_wda":true,"recovery_owner":"daemon", "wda_actionable":true,"drivable":true}
# Then act and inspect the HTTP status $ MUTATION="X-Phone-Control: 1" $ curl -H "$AUTH" -H "$MUTATION" -X POST "$HOST/agent/input" \ -d '{"type":"tap","label":"新备忘录"}' $ curl -H "$AUTH" -H "$MUTATION" -X POST "$HOST/agent/input" \ -d '{"type":"text","text":"你好世界"}'

What it promises now

WDA is a default dependency

Direct requires complete WDA setup. A running daemon alone is not proof that video or control works.

Acknowledged HTTP control

/control and /agent/input do not confuse “accepted” with “executed.” On 504 outcome_unknown, inspect the screen/status and never replay blindly.

Elements and Unicode

/agent/elements exposes the phone accessibility tree; WDA sends text without the Mac keycode path.

No Direct TCC identity

The installer preserves a valid signature and applies ad-hoc signing only when needed. Stable TCC identity exists only for legacy mirror.

Mirror is compatibility

Only explicit PHONE_REMOTE_BACKEND=mirror enables ScreenCaptureKit, WebRTC, TURN, CGEvent, and their TCC permissions.

Layered hardware evidence

WDA components have records. Installer, MJPEG, browser gestures, recovery, and multi-device behavior still need the full acceptance run.

Phase 1 network boundary

The daemon password, cookie, and bearer protect port 44321 only. WDA's device-side 8100/9100 services have no authentication. USB iproxy pins the Mac relay to a device but cannot stop another host on the routable LAN from reaching WDA directly. Run this release only on a trusted, isolated network. A Phase 2 companion app or controlled tunnel must provide the real device-transport authentication boundary.
