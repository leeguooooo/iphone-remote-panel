iphone-use — Agent API

Direct-to-device HTTP control for agents, MCP clients, scripts, and the browser companion.

An agent drives the iPhone by talking to the already-running daemon over HTTP. PHONE_REMOTE_BACKEND is fixed when the daemon starts: direct (the default) uses WebDriverAgent for on-phone input and WDA MJPEG for video; mirror is the explicit legacy iPhone Mirroring + ScreenCaptureKit + CGEvent backend. Direct mode needs no iPhone Mirroring, Screen Recording, Accessibility grant, Mac cursor, or frontmost window.

The backend is a deployment boundary, not a health-based fallback. A direct request that WDA cannot perform fails closed. It never wakes iPhone Mirroring or injects into the Mac. To use the legacy path, set PHONE_REMOTE_BACKEND=mirror and restart the daemon.
Direct requires completed WDA setup. Installing or starting the daemon does not make the phone ready. Run ~/.iphone-use/setup-wda.sh doctor, ~/.iphone-use/setup-wda.sh, and ~/.iphone-use/setup-wda.sh status with the pinned iPhone connected, trusted, unlocked, and awake. Human operators can open /setup for the auth-gated live connection guide; it reads status only and enables /phone when backend:"direct" and drivable:true.
Phase 1 network boundary: daemon auth protects port 44321, not WDA's unauthenticated device-side 8100/9100 services. USB iproxy pins the Mac relay to a device but does not block direct LAN access to the phone. Use a trusted, isolated network until a Phase 2 companion or controlled tunnel supplies authenticated device transport.

Authentication

Machine callers authenticate with a bearer token. Browser-facing reads (/agent/status, /agent/screenshot, /agent/mjpeg) and /agent/mode also accept a valid browser session cookie. /agent/input and /agent/elements require the bearer path. Bearer selection has two modes:

ModeWhenToken to use
Dedicated token PHONE_REMOTE_AGENT_TOKEN is set on the daemon That token — the password is no longer accepted as a bearer
Password fallback (legacy) PHONE_REMOTE_AGENT_TOKEN is unset PHONE_REMOTE_PASSWORD 
Authorization: Bearer <PHONE_REMOTE_AGENT_TOKEN or PHONE_REMOTE_PASSWORD>

When the daemon runs with no password and no agent token (open LAN-dev mode) the agent API is open too — the same policy as the browser cookie gate. The bearer is compared in length-checked constant time.

State changes have a second, explicit intent gate. Every state-changing POST must include the exact header X-Phone-Control: 1, including /control, /agent/input, /agent/actions, /agent/mode, and POST /agent/inbox and /agent/inbox/drain. This is a CSRF/intent guard in addition to bearer or session authentication; it does not replace authentication. GET requests do not need the header. The bundled browser and MCP clients add it automatically. A missing or different value returns a self-describing 403 response with required_header and a retry hint: {"ok":false,"error":"missing_control_header","required_header":"X-Phone-Control: 1",…}.

When update_available is true, upgrade with the install one-liner — the web client shows the same hint as a banner.

POST /agent/mode

This is current-backend recovery, not a mode switch. It never changes PHONE_REMOTE_BACKEND. Direct accepts only mode=agent to restart daemon-managed WDA; Mirror accepts only mode=mirror to recover the legacy Mirroring session. A cross-backend value returns 409. In Direct, the canonical classic UDID must already be persisted as PHONE_REMOTE_UDID; a request cannot establish or temporarily change it: 

MUTATION="X-Phone-Control: 1"
# first require target_configured:true in /agent/status
curl -s -H "$AUTH" -H "$MUTATION" -X POST "$HOST/agent/mode" -d '{"mode":"agent"}'
# poll /agent/status until wda_actionable:true and drivable:true

# a different request-scoped udid returns HTTP 409 target_change_requires_restart
curl -s -H "$AUTH" -H "$MUTATION" -X POST "$HOST/agent/mode" -d '{"mode":"mirror"}'
# HTTP 409 in direct backend:
# {"ok":false,"error":"backend_is_direct",
#  "hint":"set PHONE_REMOTE_BACKEND=mirror and restart the daemon to use the legacy compatibility backend"}

mode=agent works only when managed_wda:true, requires ~/.iphone-use/setup-wda.sh and an unlocked, awake phone, and is asynchronous. During startup, status reports reconnecting:true. A concrete setup prerequisite failure takes precedence: device_state becomes "blocked", setup_blocked_on names the cause, and hint gives the operator action instead of telling clients to keep waiting. With no blocker, setup_phase and setup_message report the live build stage; clients must keep treating drivable:true as the only permission to act. When recovery_owner:"external", the endpoint returns 409 wda_is_externally_managed; recover the service on its owning host.

A daemon deployed with PHONE_REMOTE_BACKEND=mirror does not construct a WDA client even if WDA environment URLs are present. Its browser reconnect action sends {"mode":"mirror"} to recover that same compatibility backend. It rejects mode=agent; changing to Direct requires a persisted configuration change and daemon restart.

The MCP phone_reconnect tool is a constrained wrapper around {"mode":"agent"}. It takes no arguments, never accepts a UDID, changes device, or falls back to Mirroring. For managed Direct it waits up to roughly 120 seconds for the persisted canonical target; an externally managed WDA endpoint returns an operator-owned recovery error instead.

POST /agent/input

Body is one JSON control message. Coordinates are normalized [0,1] over the WDA window (0,0 = top-left, 1,1 = bottom-right). Direct gestures are atomic: use tap, long-press, swipe, or drag rather than Mirroring-era down/move/up streams.

MessageDirect/WDA effect

{"type":"tap","label":"新备忘录"}Tap only when the exact visible label has one match in a fresh element tree. Zero, multiple, or non-actionable matches return 422 with outcome:"not_sent".

Supported fields match wait_for: label, identifier, kind, value, focused, enabled, and visible.
{"type":"tap","element":3,"snapshot":"…"}Tap the centre of element index 3 only if the current tree still matches the ephemeral snapshot returned by the same /agent/elements response.
{"type":"longpress","x":0.4,"y":0.6,"duration_ms":700}One complete long-press; default duration is 600 ms. No matching up is needed.
{"type":"swipe","x1":0.5,"y1":0.8,"x2":0.5,"y2":0.2}One complete swipe from start to end; optional duration_ms.
{"type":"drag","x1":0.4,"y1":0.6,"x2":0.7,"y2":0.3}Hold then drag; optional hold_ms (default 500) and duration_ms.

Direct mode returns 200 only after the WDA action succeeds. /agent/input adds no deadline field to the action payload; the server applies a fixed 15-second total deadline from request receipt, including WDA mutex waiting and execution. Invalid JSON returns 400; a wrong bearer returns 401; auth lockout returns 429; an unsupported atomic WDA command can return 422; a down, missing, or unsupported WDA path returns 503 with "fallback":"disabled". An idle-released device also returns 503 plus Retry-After: 5 while WDA restarts.

Snapshot refs are intentionally short-lived. If the element tree changes before an indexed tap, the server returns 409 stale_element_snapshot with retry_safe:true and sends no tap. Fetch /agent/elements again and choose again. Recorded flows should persist accessibility labels or another stable locator, never an element index or snapshot token.
Label taps are strict, not “first match wins”. Exact-label resolution returns 422 element_not_found, ambiguous_element_label, or invalid_element_target before sending an action. When a label is repeated, use /agent/elements to disambiguate by identifier, kind, or state, then submit its index with the same snapshot token.
Destructive operation: {"type":"uninstall","bundle":"com.example.app"} removes that app and its data through devicectl. It is bearer-gated but irreversible at the API level. Configure PHONE_REMOTE_UDID before starting the daemon on a multi-device Mac; if a request includes udid, it must match that canonical target.

POST /agent/actions

Use this endpoint after a flow segment is understood and its stable locators and postconditions are known. One request can contain at most 24 steps. The daemon validates the entire JSON sequence before dispatching the first mutation, then holds one WDA control lock so another daemon client cannot interleave gestures. The first failed action, expectation, read, lifecycle transition, or deadline stops the sequence; every later action remains unsent. 

{
  "steps": [
    {
      "kind": "action",
      "action": {"type": "shortcut", "name": "home"},
      "after_ms": 300
    },
    {
      "kind": "wait_for",
      "expect": {
        "present": [{"label": "搜索"}],
        "absent": [{"label": "确认付款"}]
      },
      "timeout_ms": 3000,
      "poll_ms": 100
    },
    {
      "kind": "action",
      "action": {"type": "tap", "label": "搜索"}
    },
    {
      "kind": "wait_for",
      "expect": {
        "application": "聚焦",
        "present": [{"kind": "TextField", "focused": true}]
      }
    }
  ]
}
Step kindContract
actionOne supported Direct/WDA input payload, including strict tap_locator and validated bundle-id launch_app. Optional after_ms is capped at 3000 ms and is only an animation settle. Destructive uninstall is never accepted in a batch.
wait_forPolls the current element tree. application is an exact Application label; every present locator must match and every absent locator must not match. Locator fields are exact label, identifier, kind, value, focused, enabled, and visible. Timeout is 1–10000 ms; poll interval is 50–1000 ms.
pauseA fixed 1–3000 ms pause for animation that exposes no semantic state. Prefer wait_for.

Declared waits across one batch are capped at 60 seconds, the request body at 64 KiB, and the server's total execution budget at 75 seconds. A success response includes completed, applied_actions, and compact per-step results. A failure includes failed_step, the completed/applied counts, completed steps, the last failed wait observation when available, outcome, and retry_safe. A read-only wait_for rebuilds one stale WDA source session within its existing deadline. The retry flag describes replaying the whole batch: once an earlier action landed, it is false even when the current failed step itself was not sent.

This is not permission to batch guesses. Discover a changing or high-consequence flow with the normal see → one action → verify loop. Batch only the stable segment, put semantic gates around page transitions, and inspect current state instead of replaying a batch after outcome_unknown or retry_safe:false.
One-command replay without a model: the release-matched iphone-use-mcp binary accepts flow validate <file.json> and flow run <file.json> --input key=value. Flow v1 contains a name, optional explicit string inputs, and the same guarded step objects exposed by MCP. Validation is offline; execution first requires a Direct daemon with drivable:true, submits exactly one /agent/actions request, and never retries. Input values are resolved only for the current invocation and are never written back to JSON. CLI arguments may remain visible in shell history or process inspection, so secrets, private content, payment, send, publish, or delete actions still do not belong in this mechanism.
Browser recorder: the /phone control bar now exposes a reviewed automation flow. It records only acknowledged actions, prefers exact accessibility labels selected through the element panel, flags coordinate taps and gestures as fragile, and converts typed text into a named runtime parameter without retaining the literal recorded value. The operator fills a fresh in-memory value before one-shot execution; downloaded JSON contains only the parameter definition. After an action, it compares bounded element-tree snapshots and appends a wait_for checkpoint only when a new unique accessibility identifier or foreground application can be proved. It never copies arbitrary screen labels or values into automatic checkpoints because those may contain names, balances, or other private content. Otherwise it visibly retains the 350 ms fallback. The operator can move an action together with its checkpoint, remove either, download valid flow-v1 JSON, or send the batch once. If another action could not be persisted, the download is explicitly marked an incomplete draft and one-shot execution stays disabled. Parameterized flows remain runnable only after every required value is filled. A later browser session can open the saved JSON, restore its reviewable steps after strict validation, fill fresh runtime parameters, and replay it without a model. Browser import rejects literal typed text so private input cannot silently survive inside the file. Complete flows still require confirmation that the reviewed steps contain no payment, send, publish, delete, or other irreversible action.

POST /control (browser)

The direct browser uses the same WDA dispatcher through a separate cookie-authenticated endpoint. Requests must include X-Phone-Control: 1; successful commands return only {"ok":true}. Every message must also include a positive ttl_ms from 1 through 2500; optional issued_at_ms is audit metadata, while freshness is enforced with the server's monotonic deadline. Missing login, missing control header/deadline, invalid JSON, WDA failure, expiry, and lifecycle transitions are explicit HTTP errors, so the UI must not clear input or show success until the response is successful.

This route exists only for backend:"direct". A daemon configured with PHONE_REMOTE_BACKEND=mirror returns 409 because the legacy browser uses its WebRTC data channel.

Direct delivery outcomes and retry safety

/control, Direct /agent/input, and every mutation step inside /agent/actions use at-most-once delivery semantics. A deadline does not automatically mean the action failed:

When the deadline firesResponseCaller action
Before the WDA action is dispatched 408
{"ok":false,"error":"not_sent","outcome":"not_sent","retry_safe":true}		 The daemon confirms nothing was sent. A caller may retry if the action is still wanted.
After dispatch, WDA reports an error or transport failure but cannot prove the action did not land 502
{"ok":false,"error":"outcome_unknown","outcome":"unknown","retry_safe":false}		 Inspect status and phone state. Treat the command as possibly applied; do not replay it blindly.
After the WDA future has started, but completion cannot be confirmed 504
{"ok":false,"error":"outcome_unknown","outcome":"unknown","retry_safe":false}		 Read /agent/status and then elements/screenshot before deciding what happened. Do not blindly replay text, scroll, Back, taps, or other non-idempotent input.

None of these responses carries Retry-After. In particular, a 502 or 504 is not permission to retry: the first action may already have landed on the phone. For a multi-step response, retry_safe also accounts for all earlier applied steps, so a later unsent failure does not make replaying the whole batch safe.

GET /agent/mjpeg

Proxies WDA's on-device MJPEG service (PHONE_REMOTE_WDA_MJPEG_URL, normally http://127.0.0.1:9100) as multipart/x-mixed-replace. It accepts either the agent bearer or a valid browser session cookie. An open stream counts as activity so idle release does not stop WDA while somebody is watching.

The daemon allows at most four simultaneous live streams. A missing MJPEG endpoint returns 503; upstream connection/stream failure is an error, not a switch to legacy WebRTC. Each open stream increments both viewer_count and mjpeg_viewer_count; only the latter excludes legacy /ws viewers.

GET /agent/screenshot

Returns a validated image/png of the selected phone. In direct backend this is WDA-only: if WDA is down or returns an invalid frame, the endpoint returns an error and does not capture iPhone Mirroring or the Mac screen. An invalid PNG, WDA error, or timeout immediately revokes cached actionability before the response returns.

The explicit mirror backend does not construct WDA. Its screenshot path captures the Mirroring window only; PHONE_REMOTE_WDA_URL is ignored there.

GET /agent/elements

Requires actionable WDA. The phone's current UI is flattened to agent-friendly rows in document order, accompanied by WDA screen dimensions: 

{
  "screen": { "width": 440, "height": 956 },
  "snapshot": "rQq8…",
  "elements": [
    {
      "kind": "Button",
      "label": "新备忘录",
      "identifier": "new-note-button",
      "rect": [369, 885, 38, 38],
      "accessible": true,
      "depth": 7
    }
  ]
}

Prefer this over /agent/screenshot when labels and structure are enough: the labels feed straight into {"type":"tap","label":…}, and array indexes feed {"type":"tap","element":N,"snapshot":"…"} using the token from the same response. Failures keep a parseable JSON body but never masquerade as a successful empty tree: transition, missing-WDA, or busy states return 503; a failed source fetch after one stale-session retry returns 502. Clients must reject non-2xx responses and then inspect error, transitioning, and /agent/status. A source failure or timeout immediately revokes cached actionability, so an older successful health probe cannot leave drivable:true behind.

Rows stay sparse for low-token callers. enabled:false and visible:false appear only when WDA explicitly reports a node as disabled or hidden; accessible:true and focused:true appear only when WDA explicitly reports them true. An absent state field is therefore not a positive assertion when an upstream source omitted that attribute. identifier and placeholder appear only when the application supplies them.

GET/POST /agent/inbox

The return path of the legacy Shortcuts RPC bridge: the phone (an iOS Shortcut's "Get Contents of URL" action) POSTs arbitrary JSON here; an agent GETs it. GET is always a read-only peek; the legacy ?peek=1 spelling remains equivalent. The append POST requires agent auth plus X-Phone-Control: 1. To consume results, use POST /agent/inbox/drain with the same auth and mutation header; it returns and atomically clears the queue. Bounded ring buffer (64), oldest dropped.

The current Shortcuts launcher depends on Spotlight, clipboard/key events, and the Mac-side Mirroring path. The inbox endpoint remains available, but the bridge itself is legacy PHONE_REMOTE_BACKEND=mirror functionality, not a promised direct/WDA capability.

Example — a see-decide-act loop

HOST=http://192.168.0.190:44321
PW=<password>
AUTH="Authorization: Bearer $PW"
MUTATION="X-Phone-Control: 1"

# 1. require the configured direct target to be actionable
curl -s -H "$AUTH" "$HOST/agent/status"
# continue only with backend=direct, wda_actionable=true, drivable=true
curl -s -H "$AUTH" "$HOST/agent/elements"

# 2. see
curl -s -H "$AUTH" "$HOST/agent/screenshot" -o screen.png

# 3. act — Home and Spotlight are supported by direct WDA
curl -s -H "$AUTH" -H "$MUTATION" -X POST "$HOST/agent/input" -d '{"type":"shortcut","name":"home"}'
curl -s -H "$AUTH" -H "$MUTATION" -X POST "$HOST/agent/input" -d '{"type":"shortcut","name":"spotlight"}'
curl -s -H "$AUTH" -H "$MUTATION" -X POST "$HOST/agent/input" -d '{"type":"text","text":"Notes"}'
curl -s -H "$AUTH" -H "$MUTATION" -X POST "$HOST/agent/input" -d '{"type":"tap","x":0.5,"y":0.22}'
curl -s -H "$AUTH" -H "$MUTATION" -X POST "$HOST/agent/input" -d '{"type":"scroll","x":0.5,"y":0.5,"dx":0,"dy":60}'

Behaviour notes

No Mac cursor in direct mode. WDA synthesizes input on the phone. The shared-cursor lease and X-Yield-To-Human behavior apply only to the explicit legacy mirror backend.
Unicode text in direct mode. WDA sends text through /wda/keys, so CJK does not take the legacy Mac-keycode/Pinyin path. The US-keycode/IME caveat remains relevant only to mirror compatibility input.
Video and screenshots are distinct health layers. /agent/mjpeg proves the 9100 live-video relay; a successful /agent/screenshot proves a single WDA PNG. Neither alone proves that input is actionable — keep gating actions on status.
System-command boundary. Direct supports Home, Spotlight, Back, keyboard dismissal, and the documented named keys. App Switcher is unsupported. Shortcuts bridge, Control Center, and other Mac/Mirroring-specific automation remain legacy until they gain a device-side implementation and hardware acceptance.

Live acceptance boundary

Source/tests and a 200 status response are not physical-device proof. Before shipping a direct integration, verify on the intended iPhone that:

  1. the daemon runs without iPhone Mirroring, Screen Recording, or Accessibility;
  2. status identifies the pinned device and reports actionable/drivable WDA;
  3. managed recovery reports releasing → released → reconnecting → ready, while an external endpoint remains owned by recovery_owner:"external";
  4. MJPEG updates continuously and a stopped 9100 relay is reported as failure;
  5. tap, long-press, swipe, drag, both scroll directions, CJK text, named keys, Home, and Spotlight each land once;
  6. Switcher fails honestly, WDA loss never moves the Mac cursor, and direct screenshot never returns mirror pixels;
  7. lock/unlock, USB reconnect, daemon/Mac restart, and a multi-device host recover the same canonical target;
  8. 8100/9100 exposure is measured on an isolated network rather than assumed safe because the Mac relay is loopback-only.
